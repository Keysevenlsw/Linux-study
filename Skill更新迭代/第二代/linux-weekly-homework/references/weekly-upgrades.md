# 每周升级与版本保留

用户要求逐周改进，升级应依托当周实际使用结果。每次完成周作业执行以下过程，单独的 PDF 重导出不必强行升级。

1. 阅读已有版本和最后一条升级记录。回看老师反馈、学生反馈、实际报错、阅读定位和 PDF 布局问题。
2. 明确本周要改进的具体行为及证据。例如某组汇编误用了架构、某张长表被裁切、老师改变了阅读范围、蓝桥实验迁移后需按名称定位。
3. 修改前将当前 skill 完整复制至课程目录 `skill历史版本/第X周升级前-v旧版本/linux-weekly-homework/`。已有同名存档时另加时间后缀，不覆盖。不要把历史版本放进 skill 自身，以免递归膨胀；不复制教材和整周作业。
4. 在源 skill 中做能验证的改进。周次特有内容放参考文件，不把某一章实验流程写死进 `SKILL.md`；重复出现的机械操作再提取脚本。保留学生原有写作风格和“助手负责教材阅读、学生自己看视频”的分工。
5. 版本规则：修正局部错误用 PATCH（如1.0.0→1.0.1）；增加能力用 MINOR（如1.0.1→1.1.0）；不兼容的接口／工作流改动用 MAJOR。同步 `SKILL.md` frontmatter 的 `metadata.version` 与 `CHANGELOG.md`。不要按日历凭空递增。
6. 更新 `CHANGELOG.md`，记录日期、对应周次、版本、实际问题、改动文件、验证与仍待处理的问题。源 skill 未使用前标“初版”，不能称已完成第四周迭代。
7. 脚本改动运行实际例子；PDF 改动必须重新导出和看图；指令改动用本周真实任务检查是否会错认要求、伪造状态或把阅读交还学生。可以用 skill-creator 的 `quick_validate.py` 验证结构；其通过不等于任务行为通过。
8. 用 `scripts/install_skill.ps1` 将源版本部署到 Codex 目录，并核验脚本打印的文件哈希比对结果。课程源版本是维护入口。Codex 本轮已加载的 skill 不一定热更新，必要时在下一次会话重新调用新版本。

## 升级条目格式

```markdown
## v新版本 · YYYY-MM-DD · 第X周

- 依据：本周实际任务或反馈。
- 问题：观察到的行为及影响。
- 改进：具体能力变化与涉及文件。
- 验证：实际命令、检查结果或行为核验。
- 保留：本周仍待处理的问题；没有则写无。
```

一次性问题只记录在当周报告，不必全部上升为永久规则。若没有观察到缺陷，可以补充经确认的课程要求与章节映射，或增加真实导出样本的验证记录；不能捏造失败案例来证明改进。

老师要求提交每周版本时，将对应 skill 目录或 ZIP 和该周升级说明一起提交。不要把所有历史 skill 一起加载到 Codex 的技能目录，否则会出现重复触发。
